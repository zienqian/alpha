01 / DECISION

支持引入 Bazel，先验证最小闭环

多语言本身并不要求更换 monorepo 工具。Bazel 更有价值的场景，是语言之间开始共享代码生成、工具链、构建产物与缓存，需要把这些关系纳入同一张依赖图。

CAPABILITY

能力上可行

Go 可使用 rules_go + Gazelle；JS/TS 可使用 rules_js + rules_ts。Bazel 按规则描述的输入、工具与输出构建，而非限制仓库只能包含一种语言。[2][3][4]

FIT FOR ALPHA

近期价值尚未量化

仓库只有 4 个 JS 工作区包，已配置 Nx 缓存；尚未发现 Go 模块或 CI 配置。当前没有构建耗时基线，不能据此承诺提速或成本下降。

RECOMMENDATION

从真实工具切入

先接一个纯 Go CLI，随后用 Provider 验证现有 TS 产物和测试。再以 Session 的 SQLite 适配器验证原生依赖，完成后决定是否推广。

建议决策：把 Bazel 列为长期构建底座候选，开展有时间上限的 PoC。若短期只是增加一个独立 Go 服务，继续用 Nx 调用 Go 原生命令也能满足需求；若出现跨语言产物依赖、可复现交付或明显 CI 压力，Bazel 的优先级提高。以上为基于仓库现状的工程判断。

本文区分三类信息：仓库事实来自本地文件；生态能力来自一手资料；目录、阶段、工期与验收阈值为本报告的建议，未表示迁移已经验证通过。

03 / TRADE-OFFS

Nx 与 Bazel 解决问题的粒度不同

Nx 可以通过自定义命令接入 Go，并根据项目图调度、缓存任务；Bazel 将输入、工具、依赖与输出细化为构建动作。实际收益取决于声明的完整性和目标拆分质量。[5][6]

比较维度A · Nx + 原生语言工具B · 渐进引入 BazelC · 一次性全量迁移
近期投入较低。新增 Go project.json，调用 go build / test。中等。新增规则、工具链和试点目标，分阶段补齐。最高。四个包、所有测试和边界检查同时适配。
开发体验保持 pnpm、Go 原生工具和 IDE 习惯。原生 IDE 体验保留；构建入口逐步切换，需要维护过渡说明。需要立即学习 labels、runfiles、工具链和 Bazel 排错。
跨语言依赖用项目依赖、inputs / outputs 和脚本显式串联；Go import 图需手工配置或插件支持。逐步形成统一目标图；适合 schema → TS / Go 生成代码这类链路。理论上一次统一，但迁移期间耦合面大。
缓存与隔离已有任务缓存；补齐源码、Go 版本、环境和输出声明。可细化到 action；工具链和输入必须完整声明，才能安全复用缓存。能力与 B 相同，全量迁移不会自动提高缓存正确性。
当前 tsrs / SQLite保持已有流程。逐个做兼容性实验，失败可停留在已完成阶段。任何一个问题都可能阻塞全仓切换。
维护成本任务配置、语言工具升级；跨语言依赖靠约定补齐。规则版本、BUILD 文件和工具链；过渡期有双系统成本。稳态也有 Bazel 成本，且前期风险集中。
适用判断短期有效备选少量独立 Go 工具 / 服务。推荐研究路线预期多语言协同，愿意承担构建维护。当前不建议缺少性能基线和兼容性证据。
避免“换一层命令外壳”。用一个 Bazel genrule 包住整仓 pnpm build，同时读取宿主 node_modules、向源码目录写 dist，只完成了入口包装。它仍可能继承隐藏输入、粗粒度重建和缓存不可靠的问题。PoC 必须验证声明输入与独立输出。[7]
A 方案具体怎么接 Go？

新增 Go 项目及其 project.json；通过 nx:run-commands 运行 build / test，构建输出到该项目的独立产物目录。缓存 inputs 应包含 Go 源码、go.mod、go.sum、共享 Go 库、工具链版本、GOOS / GOARCH / CGO 设置。跨项目依赖需显式登记。纯 Go 目录无需为了 Nx 而加入 pnpm workspace。当前仓库的 Nx schema 已包含 command、inputs、outputs、implicitDependencies；官方文档也支持自定义命令。[5]

这条路线可以直接服务短期需求，后续再把同一项目接入 Bazel；没有必要先迁走全部 TypeScript 包。

Go：先一个 module

首个 Go 工具使用根 go.mod，实际 module path 由仓库地址确定。服务、工具及共享库可放在同一个 module 内；独立部署不等于必须拆 module。

出现独立版本发布或明确隔离需求时，再拆多个 module，并按需要引入 go.work。Bazel 侧通过 Gazelle 的 go_deps 读取依赖，BUILD 中仍需明确 deps。[2]

TS：继续由 pnpm 管依赖

保留当前 apps/* 与 packages/*。纯 Go services / tools 不加入 pnpm workspace；若 tools 中出现 JS 包，再精确加入相应路径。

rules_js 导入 pnpm 锁文件并构造受控的依赖布局；这与把开发机现有 node_modules 直接作为构建输入不同。[11]

语言之间共享协议与产物。Go 服务通过 HTTP / RPC 与 TS 调用方交互。出现真实需求后，再由 schemas 生成客户端；Bazel 不会自动让 Go 直接调用 TypeScript 库。
版本 / 依赖文件保留的职责更新原则
package.json + pnpm-lock.yamlJS 依赖约束、已解析的版本与完整性信息。使用固定 pnpm 更新；验证当前 lockfile v9、workspace:*、peer / optional 依赖导入。
go.mod + go.sumGo 模块需求与内容校验；go.sum 不是传统意义上独立的版本锁文件。固定 Go SDK；go mod tidy 与 Gazelle 更新作为显式维护步骤，CI 检查无漂移。
MODULE.bazel + MODULE.bazel.lockBazel 模块与扩展解析；不能替代语言侧所有依赖清单。选定规则兼容组合后生成、提交锁文件；CI 验证锁定解析结果。
.bazelversion + 工具链声明Bazel、Node、Go、编译器的精确版本。用 Bazelisk 选择 Bazel 版本；避免宿主环境静默更换编译器。[12]

06 / INTEGRATION DESIGN

先选编译器策略，再设计 BUILD

Bazel 9.0 已移除 WORKSPACE 逻辑，新方案使用 MODULE.bazel / Bzlmod。建议以 Bazel 9 LTS 系列为候选，在 PoC 中核验 rules_go、Gazelle、rules_js、rules_ts 的精确版本组合；这不是已经验证过的兼容矩阵。[1]

TS 路线 1 · 低定制成本候选

rules_ts + 固定 tsc

使用标准 ts_project 对接 TS 编译、声明文件和依赖传播。先拿 Provider 比较现有 tsrs 的类型诊断、.d.ts、ESM exports 和行为测试。[4]

代价：这是编译器变更。当前 TypeScript 6 与 tsrs 的 TS 7.1 beta 语义不能视为相同，需独立评估，不能随构建迁移悄悄替换。

TS 路线 2 · 保留现有编译器

为 tsrs 建立受控 action

以 rules_js 的工具执行能力或自定义规则封装 tsrs，显式声明源码、tsconfig、包清单、类型依赖、平台二进制与输出。先验证 Provider。

代价：输出预测、声明传递、执行平台、可选平台包和缓存语义都需要维护。能启动 tsrs 命令不等于完成 Bazel 集成；当前未证实开箱即用支持。

现有任务Bazel 接入方向必须保留的语义
buildTS 编译 target；Go go_library / go_binary。.js / .d.ts 布局、NodeNext、package exports、运行时依赖及正确 deps。
typecheck独立类型检查目标或编译目标的明确检查入口。包括 src 与 test/tsconfig；部分类型测试需要已构建的自身公开包接口。
testJS 测试规则运行现有 node:test；Go go_test。声明测试脚本、helpers、worker、产物、包清单、配置和工具；使用测试临时目录存 SQLite 文件。
lint / boundaries声明 ESLint 输入并运行；BUILD visibility 限制目标可见性。visibility 约束目标依赖，不能独自识别 TS import type 或 package exports；保留源码与产物检查。[8]
start / live本地运行目标与独立的显式联调入口。离线测试保持确定性；真实 LLM、密钥、网络费用不进入默认 build / test 或可缓存测试。
pack / deploy（未来）显式打包目标，再由交付流程发布。JS 包包含 manifest + 正确 dist；Go 二进制按目标平台构建。镜像、注册表和服务编排另行设计。

未来接 Rust / Python 时，哪些设计可以复用？

统一入口、目标依赖、工具链固定、缓存与验证方法可以复用；依赖导入和运行环境仍需使用对应规则集。Rust 可考察 rules_rust，Python 可考察 rules_python。含 C 扩展、平台 wheel 或 native build script 的依赖，需要再次做平台验证；当前不引入这些语言的额外配置。[14][15]

07 / MIGRATION RISKS

真正的工作量，在运行环境与行为等价

风险Alpha 中的具体触发点验证与处理
编译器兼容高 · 决策门槛tsrs 实验版本；TS 6 工具链并存；NodeNext、声明输出和公开类型测试。双路线 Provider spike。记录诊断差异与 API 产物差异；不能只看 build 退出码。
SQLite 原生模块高 · 推广门槛better-sqlite3 安装脚本、原生 .node 文件与 Node ABI。固定 Node，验证 Windows / Linux 的预构建或本地编译路线；生命周期脚本显式配置，检查原生文件进入 runfiles。缺预构建产物时需要相应编译环境。[11][13]
测试运行文件高相对 ../dist、动态扫描 .test.js、spawnSync(process.execPath)、worker / loader、读取兄弟包源码。在 Bazel 输出树重建受控布局或调整测试定位；显式声明所有 data。不能依赖源码目录残留 dist 或本机已安装 node_modules。
边界检查退化高@nx/enforce-module-boundaries 依赖 Nx 图；Session 与 ADK 的 type-only 约束和 exports 测试。过渡期保留 Nx 相关校验。退出 Nx 前，用等价静态规则 + 负例验证覆盖；Bazel visibility 只是补充。
Windows 与 ESM中高原生 Windows 开发、长路径、symlink / runfiles、ESM 解析与子进程。短输出路径、PowerShell 调用；按所选规则要求核验链接能力和 launcher。rules_js 文档仍列出 ESM 逃逸 runfiles / sandbox 的已知问题，需审查选定版本，额外用干净 Linux 环境验证隔离。[9][3]
缓存正确性中高编译器版本、环境变量、原生安装脚本、外部网络、遗漏文件输入。先完成干净构建与失效实验，再开共享缓存；区分 OS / CPU / 工具链，可信 CI 写、开发端初期只读；不缓存带密钥的真实联调。
Go / IDE 两套视图中Go modules 与 BUILD deps；未来 codegen 文件；gopls 导航。保留 go.mod 与语言服务；固定 SDK，自动维护 BUILD 并做无漂移检查。第一阶段用纯 Go，cgo 作为独立验证范围。
冷启动与维护负担中下载 Bazel、语言 SDK、规则和依赖；新增 BUILD 文件与版本升级。分别测量初次下载、冷 action、热增量；指定维护人。为规则升级建立小范围验证，按真实瓶颈再做镜像 / 缓存优化。
必须保留当前离线边界。Provider 的默认 test 只运行 provider.test.js；真实 OpenRouter 测试是独立入口。ADK 的 test:live 也是显式入口。迁移时不可用泛化文件扫描把这些真实服务测试纳入默认套件。

Windows 上不能把“Bazel 支持 Windows”直接解释为所有语言规则、安装脚本和 sandbox 行为都与 Linux 相同。本报告建议用原生 Windows 验证开发体验，以干净 Linux CI 验证交付环境；若未来 CI 并非 Linux，应替换成实际目标平台。

推进到统一 Bazel 的条件

  • Go、TS 和原生依赖均跑通真实测试。
  • tsrs 的保留或替换已有明确决定。
  • 边界检查与公开包接口没有退化。
  • 构建收益或一致性交付价值覆盖维护成本。
  • 有明确负责人维护规则与工具链升级。

以上均为待验收条件；圆圈并不表示已检查。

退出与回滚策略

阶段回退：若 TS 迁移成本过高，可只保留 Go 的 Bazel 试点；现有 TS 继续由 Nx 管理，记录复评时间，避免无限期双份配置。

完整撤回：试点提交单独管理，移除新增构建配置并恢复便捷入口；保留业务 Go 代码，通过 go build / test 或 Nx 运行。旧 pnpm 锁文件、scripts 与 dist 约定在验收前保持可用。

暂缓条件：tsrs 与规则无法可靠适配、SQLite 依赖宿主隐式环境、边界检查无法等价覆盖，或到达人日上限仍缺少闭环。

下一步的具体范围：新增 Bazel 基础配置 + 一个纯 Go CLI + Provider 的独立验证目标；保留现有 pnpm / Nx 命令。完成这一个切片后，再决定是否迁移 ADK、Session 与示例应用。本报告未安装 Bazel、未生成 BUILD 文件，也未修改仓库构建入口。
