02

问题是职责堆在了一起

当前对象已经超过“启动目录”的含义。它同时是文件系统入口、搜索器、命令执行器、目录独占锁和资源管理器。这些能力各有用途，但不需要由一个 Workspace 接口统一持有。

CURRENT / FACTORY

构造目录，附带启动基础设施

local/local-workspace.ts 在创建时校验 Windows / PowerShell，查找并运行 pwsh、rg，构造环境变量和锁目录。只想读取文件也得经过这些步骤。

CURRENT / LIFETIME

Agent 生命周期绑着目录锁

coding-plugin.ts 在 start 时 acquire，在 dispose 时 release。bridge 的 BOOT → LOCK → LOCKED 握手把 Windows 进程管理和跨进程目录独占绑在一起。

CURRENT / STATIC TOOLS

上次只完成了定义层的解耦

六个 tool 已经是模块级常量，但执行仍进入 tools.ts 的统一分发函数。连 read / list / search 也先检查 plan + lease，静态工具还不能独立执行。

CURRENT / CALLER

应用负责不必要的资源收尾

apps/alphacode/src/runtime.ts 要依次创建、关闭 workspace，并借用 workspace.id 作为会话 namespace。目录身份本可直接从规范化路径计算。

为什么最初会长成这样？ 从现有接口看，它试图用统一适配器承载本地执行、隔离等级和独占写入。对目前只有本地 Bun CLI 的范围，这层抽象偏重。未来如果真有远程执行需求，再为具体能力增加接口即可。

IMMUTABLE / LAUNCH CONFIG

cwd 固定，但不做可变全局单例

入口按“路径参数 → ALPHACODE_WORKSPACE → 启动时 process.cwd()”取值，再 realpath 并校验目录。传入 Agent 后保持不变。工具不会在每次执行时重新读取 process.cwd()，也不用 process.chdir() 改共享状态。

MUTABLE / AGENT STATE

状态与目录分开

export const readFileTool = createTool({
  name: 'read_file',
  description: 'Read a UTF-8 file before editing it.',
  input: readFileSchema,
  effect: 'read',
  async execute(args, ctx: ToolContext<CodingContext>) {
    const snapshot = await readSnapshot(ctx.app.cwd, args.path, ctx.signal);
    if (!snapshot) return encodeFailure('FILE_NOT_FOUND');
    ctx.app.state.observations.set(snapshot.path, snapshot.revision);
    return encodeReadResult(snapshot, args, ctx.app.state.budget);
  },
});

职责建议归属约束
目录与路径检查cwd + 普通函数保留越界、符号链接和 Windows 特殊路径检查；命令可操作宿主机，cwd 本身不是沙箱。
工具定义与执行六个独立 tools/*.ts直接导出常量；输入 schema、工具预检、execute 在各自模块；索引文件只聚合。
权限与预检内部 permissions.ts沿用 ADK authorizeTool hook。按静态工具名表找预检函数，移除统一业务分支；本轮不改 ADK 工具协议。
调用状态每个 Agent 的内部 contextcwd / shell / data / controls / state；shell 是只读执行环境描述，原 app 字段改名 data。状态不作为稳定公共 API。
命令生命周期process/run-command.ts + cross-spawn采用 OpenCode 的进程组 / taskkill 与输出截止策略；项目保留一个集中适配模块，对接 AbortSignal 和 ADK 关闭流程。
会话目录身份AlphaCode 会话初始化保留现有 Windows 规范路径小写后 SHA-256 的 local: namespace，避免会话看起来“丢失”。
预检和独立工具如何兼容？为什么不把所有状态一起删掉？

各工具模块同时导出自己的预检函数，permissions.ts 使用一张普通静态表按 name 查找。读操作生成权限描述后直接执行，不依赖计划缓存；edit / create / command 的预检产物以当前 call key 暂存，批准后由同一工具消费。拒绝、取消和 run.end 都清理对应记录。

写入预检包含具体目标、预期版本和变更内容；执行前再次校验。审批不能只绑定工具名或一个可重新解释的参数。保留这小块调用状态，可以维持“看见的变更就是批准的变更”。未知副作用仍交给 ADK 按现有规则处理，不能改成普通成功结果。

静态表只是内部函数查找，不增加新的注册器、依赖注入容器或远程文件系统接口。公共入口收敛到 createCodingAgent、静态 tools 和必要的选项类型；context / plugin 的组装留在包内。

平台默认候选顺序模型应知道什么
Windowspwsh → Windows PowerShell → 可用 Git Bash → COMSPEC / cmd.exe实际选中的 family / 路径 / 可确认的版本。只有 PowerShell 5.1 时按其语法生成命令，不能套用 Bash 或 PowerShell 7 语法。

与上游的明确差异：AlphaCode 给 macOS 的 zsh 兜底再加可用性检查；自定义路径无效时直接报告配置错误。Windows 可补查系统目录以覆盖 PATH 不完整的安装。所有候选在生成命令前确定，不在一次已批准的执行中临时换 shell。

场景： 新 Windows 用户没有 Git、没有 PowerShell 7 → 使用系统 Windows PowerShell。传给模型的环境说明写明 shell: Windows PowerShell 5.1；模型生成 PowerShell 命令。Git Bash 是可选能力，不是启动门槛。所有 shell 都不可用时，只将命令工具标记为不可用，聊天与文件工具继续工作。

薄适配职责采用的行为上游证据 / 我们的边界
参数POSIX shell 用 -c；PowerShell 用 -NoLogo / -NoProfile / -NonInteractive / -Command；cmd 用 /c。参考 ShellSelect.args。宿主选择解释器，模型只提供 command；仍需验证 Windows 引号与编码。
取消与超时Windows 请求 taskkill /T /F；Unix 发送进程组信号，约 3 秒后升级 SIGKILL；失败回退单进程终止。参考上游 killGroup / stop。退出码与取消原因分开记录，取消不是“未执行”。
输出结束区分 exit 与 close；根进程退出后给管道有限收尾时间，上游采用 1 秒，避免后代一直持有管道导致挂起。参考 CrossSpawnSpawner 的 stopOutput / discard。超过截止时间需标记输出可能不完整。
结果与事件两路增量解码、有限缓存、持续排空；启动失败、退出、超时、取消、输出截断分别表达。对接既有 command.output 与工具结果；不新增持久 shell 会话或后台任务系统。
审批批准 cwd + 实际 shell + command 的组合。若 shell 失效，返回明确错误，重新选择和生成命令后再走审批。这是 AlphaCode 对静态工具和现有权限机制的接入约束，避免批准 Bash 后执行 PowerShell。

正常取消采用上游的进程树 / 进程组策略，仍有宿主强杀、脱离进程组及 Windows 根 PID 已退出等边界；不承诺所有异常下清除全部后代。目录、工具和执行层的拆分也不因此恢复 Workspace 或自研 Job Object bridge。

INTENTIONAL CHANGE

建议取消整个目录的长期独占

移除“一个 Agent 活着，整个目录就被占用”的跨进程锁。多实例可以读取同一项目，也可能同时编辑。

版本复核能发现多数陈旧修改，但“检查后再替换”不是跨进程原子 compare-and-swap。此方案不承诺并发写入串行化；如果产品确实需要，再单独设计写入临界区锁。这个行为变化在下方单独 review。

三端迁移还涉及文件与路径： Windows 的盘符、大小写、保留名称检查不能原样强加给 macOS / Linux。文件层保留通用越界 / 版本检查，并处理必要平台差异；会话 ID 在 Windows 保持旧格式，其他平台保留路径大小写。换执行库不会替代这些文件语义。
