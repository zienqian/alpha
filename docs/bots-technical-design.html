AlphaCode Bots 技术方案设计

放弃单一全局 Personal Agent 思路，转向以 Up.computer Bots 为产品外壳（多角色常驻 Bot、唯一永久对话、单项目严格绑定、清晰状态聚合与可演进专属记忆）、以 DeepSeek Super-agent 为每 Bot 内部执行引擎（Router/Worker 双层隔离、全双工异步派发、Git Worktree 并发写隔离、聚合审批、链式召回与 Watchdog）的统一架构方案。

状态：技术方案评审稿 v1.0（待确认后实施） 参考实现：krl-gr/upcomputer (Bots) + DeepSeek Super-agent 适用范围：alphacode-app-server / alphacode-web / alphacode-app 100% 离线可读 HTML + 可交互原型

01转型动机与已锁定核心决策

此前我们尝试的「单一全局 Personal Agent」在产品形态上存在两个天然张力：一方面，把所有项目、所有角色（内核开发、发版运维、文档调研）混在唯一一条主对话流中，长期运行后语义边界会逐渐模糊；另一方面，用户心智中更习惯按职责划分多个常驻伙伴（例如“Alpha 架构师”、“发布助手”、“前端专家”），每个伙伴专注一个工作仓库、拥有独立的永久对话与人格指令。

借鉴开源项目 Up.computer 的 Bots 设计，同时在每个 Bot 内部坚持使用 DeepSeek Super-agent 双层并发架构，恰好实现了“外层按角色与项目切分清晰上下文边界，内层由 Router/Worker 消除单会话阻塞”的黄金组合——这也与 Super-agent 论文 §8.3 所提出的“需要共享上下文的范围共用同一个实例，需要隔离的范围则各自独立配备”完全一致。

决策 1 · 单项目严格绑定 严格对齐 Up.computer：每 Bot 仅绑定 1 个工作项目

每个 Bot 绑定唯一 projectId，其永久对话与所有派发的后台 Worker 均收敛在该项目内；允许在空闲时通过设置页切换项目（历史对话、记忆与历史任务原项目归属均完整保留）。

决策 2 · 极简任务形态 不引入独立 Tasks 看板与手工 Worker 模板

舍弃 Up.computer 中较重的独立 Tasks 看板与自定义 Worker 触发器配置；每个 Bot 内部直接由 Super-agent Router 动态派发隔离 Worker，在对话内通过「顶部活跃任务胶囊 + 右侧 Worker Inspector 抽屉」完成进度查看、审批、Steer 与 Diff 合并。

决策 3 · Phase 1 聚焦闭环 先打通 Bots 产品外壳 + 每 Bot 独立 Super-agent 内核

Phase 1 聚焦：侧栏 Bots 分区与设置页、唯一永久对话、每 Bot 独立 Router/Worker 双层模型配置、Git Worktree 并发写隔离、聚合审批与 Worker 抽屉。长期记忆（bot_memories）、历史搜索、会话转 Bot 与 @Bot 跨会话提及在架构与 Schema 层提前预留，Phase 2 零返工接入。

决策 4 · 代码重构路径 评审确认后，将未提交的 personal 原地重构为 bots

工作区当前未提交的 src/personal/* 已实现 Super-agent 核心底座（WorktreeManager / WorkerPool / Router / EventBus / Watchdog），评审定稿后直接泛化重构为多 Bot 引擎并彻底移除 personal 入口，避免双套历史包袱。

03系统总架构全景图

系统由 BotManager 统一托管多个逻辑隔离的 Bot 实例。每个 Bot 独占自己的常驻 Router Session、Event Bus、Thread/Trigger/Link 引用图与（Phase 2）专属记忆；底层的并发执行槽位 WorkerPool、WorktreeManager 与 L1 Watchdog 在进程内共享以统筹算力与磁盘资源，并通过 bot_id 实现严格的数据与事件隔离。

04Bot 生命周期、单项目绑定与边界处理

与 Up.computer 一致，每个 Bot 严格绑定一个工作项目（projectId），拥有一条唯一永久对话。但由于 AlphaCode Bot 内部运行的是无执行工具的 Super-agent Router Session，在项目切换、项目删除与 Bot 销毁三个边界上需要更严谨的工程保障。

流程图 2 · Bot 创建、单项目绑定、安全切换与归档/删除生命周期
严格保护未合并 Worktree 与 Session agentKey 契约一致性
单项目绑定下的跨仓提示：严格对齐 Up.computer 策略——每个 Bot 的 dispatch_task 自动锁定到该 Bot 当前绑定的 projectId（Router 工具入参中不再暴露任意 projectId，从工具签名层杜绝跨仓误操作）。若用户有多个项目，建议按项目职责创建各自专属 Bot（如“Alpha 后端 Bot”、“Web 前端 Bot”）。

05每 Bot 内部 Super-agent 引擎与全双工并行调度

每个 Bot 内部完整落位 DeepSeek Super-agent 的双层核心：常驻 Router Session（只沟通、只编排、绝不亲自改代码） + 隔离并发 Worker（复用 Coding Agent 完整执行工具，在独立上下文与 Git Worktree 中干活）。

Router 控制面工具集（严格隔离底层 Coding 工具）

依据 Super-agent 论文 §7.1 消融实验结论：Router 严禁挂载 read_file、edit_file、create_file、run_command、search 等工具，防止模型自行干活导致对话阻塞。所有工具由宿主自动注入当前 botId 与绑定 projectId：

工具名阶段行为与返回语义阻塞特性
dispatch_taskPhase 1在本 Bot 绑定的 projectId 内派发隔离 Worker（参数：goal、title?、accessMode: "readonly"|"write"、threadId?），返回 { status: "started", taskId, shortId, isolationMode, worktreeBranch? }异步立即返回
steer_taskPhase 1向本 Bot 名下运行中的指定 Worker 发送纠偏或补充要求（校验 task.botId === currentBotId）异步立即返回
cancel_taskPhase 1中止本 Bot 名下指定排队/运行中的 Worker（可选清理空 Worktree）立即返回
list_statePhase 1返回本 Bot 绑定项目信息、活跃/近期任务摘要与待审批清单只读快返
recall_objectPhase 1按对象 ID（tsk_ / trg_ / thr_ / art_）在本 Bot 作用域内执行 Chain of Recall 链式召回只读快返
subscribe_thread / unsubscribe_threadPhase 1维护本 Bot 内 Thread 与 Worker 的多对多订阅，使已订阅事件走 Fast Path 直通 Worker立即返回
bot_remember / bot_forget / bot_memoryPhase 2读写本 Bot 专属事实记忆（owner="user" 锁定保护；Worker 严禁挂载写记忆工具）只读/轻写快返
bot_history_searchPhase 2全文搜索本 Bot 永久对话中已被上下文压缩折叠的早期历史记录只读快返
多 Bot 公平调度（Fair Scheduling）：全局并发池默认 maxConcurrentWorkers = 4（可配 1..12），单个 Bot 默认并发配额 perBotMaxWorkers = 2（可在 Bot 设置覆盖 1..4）。调度器采用按 Bot 轮询（Round-Robin）出队，保证 Bot A 即使一次性排入 5 个任务，也不会饿死 Bot B 的新请求。

07三级模型配置继承与链式召回（Chain of Recall）

每个 Bot 既可以零配置开箱即用（Router 与 Worker 自动共用全局默认模型），也可以按角色单独配置（例如 Router 用响应极快的轻量模型，Worker 用高智商编码模型），也可以显式配置为相同模型。同时通过稳定逻辑 agentKey 与引用图 bot_links 保障长周期永久对话不断裂、不超窗。

08SQLite 数据模型设计（sessions.db.bots.db）

独立存储于 ${databasePath}.bots.db（SQLite WAL 模式），与 sessions.db、.context.db、.artifacts.db 物理分离，绝不改动现有 Session formatVersion=1 归档格式。以下表结构完整覆盖 Phase 1，并在文末给出 Phase 2 预留表定义，确保演进零破坏性迁移：

-- ============================================================================
-- Phase 1 核心表（bots.db）
-- ============================================================================

-- 1. Bot 实体与身份配置（每 Bot 严格绑定 1 个 project_id）
CREATE TABLE bots (
  id TEXT PRIMARY KEY,                      -- 例如 bot_9f3a21bc
  name TEXT NOT NULL,
  instructions TEXT NOT NULL DEFAULT '',
  project_id TEXT NOT NULL,                 -- 严格绑定单个已登记项目 ID
  appearance_json TEXT NOT NULL,            -- { shape, color, icon/badge }
  permission_mode TEXT,                     -- NULL=继承项目/全局 | 'ask' | 'auto' | 'full'
  max_concurrent_workers INTEGER,           -- NULL=继承全局 perBotMaxWorkers (1..4)
  router_model_json TEXT,                   -- NULL=继承 | { modelId, baseURL?, apiKeyEnv?, noAuth?, contextWindow?, maxOutputTokens? }
  worker_model_json TEXT,                   -- NULL=继承 | 同上（可与 router 相同）
  router_session_id TEXT NOT NULL DEFAULT 'main',
  sort_order INTEGER NOT NULL DEFAULT 0,    -- 侧栏手动拖拽排序权重
  memory_mode TEXT NOT NULL DEFAULT 'alphacode', -- Phase 2 预留: 'alphacode' | 'off'
  last_visited_at TEXT,                     -- 用于计算未读完成/失败状态点
  archived_at TEXT,                         -- NULL=活跃，非 NULL=已归档
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idx_bots_active_order ON bots(archived_at, sort_order, created_at);

-- 2. 每 Bot 事件线索（Thread）
CREATE TABLE bot_threads (
  id TEXT PRIMARY KEY,                      -- 每 Bot 默认主线索 thr_main:<botId>
  bot_id TEXT NOT NULL REFERENCES bots(id) ON DELETE CASCADE,
  channel TEXT NOT NULL DEFAULT 'desktop-app',
  external_key TEXT,
  title TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active',
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idx_bot_threads_bot ON bot_threads(bot_id, updated_at);

-- 3. Spill 负载存储（长输入 / Diff / 报告）
CREATE TABLE bot_payloads (
  id TEXT PRIMARY KEY,
  bot_id TEXT NOT NULL REFERENCES bots(id) ON DELETE CASCADE,
  content TEXT NOT NULL,
  created_at TEXT NOT NULL
);

-- 4. 事件日志（Trigger，按 bot_id 隔离排队与 Batch 聚合）
CREATE TABLE bot_triggers (
  id TEXT PRIMARY KEY,
  bot_id TEXT NOT NULL REFERENCES bots(id) ON DELETE CASCADE,
  thread_id TEXT NOT NULL REFERENCES bot_threads(id) ON DELETE CASCADE,

  origin_trigger_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  finished_at TEXT
);

  PRIMARY KEY (bot_id, from_id, to_id, relation)
);
CREATE INDEX idx_bot_links_from ON bot_links(bot_id, from_id);
CREATE INDEX idx_bot_links_to ON bot_links(bot_id, to_id);

HTTP / SSE 接口清单（双层 SSE 避免全量聊天流广播膨胀）

MethodPath语义与状态码
GET/api/bots获取所有活跃（及可选归档）Bot 的摘要列表与聚合状态（BotSummaryView[]）
GET/api/bots/events全局索引 SSE：仅推送 Bot 摘要列表、聚合状态与全局待审批计数（轻量 < 5 KB，驱动侧栏实时更新）
POST/api/bots创建新 Bot（校验 name、projectId 存在且有效），返回 201 + BotSummaryView
PATCH/api/bots/order批量保存侧栏 Bot 拖拽顺序 { botIds: string[] }
GET / PATCH/api/bots/defaults读取与修改 config.yaml 中全局 bots 默认配置（并发数、默认 Router/Worker 模型；脱敏不返密钥）
GET/api/bots/:botId/state获取单个 Bot 的全量运行快照（Router 对话流、任务列表、Worktree 状态、待审批项、生效模型与上下文用量）
GET/api/bots/:botId/events单 Bot 详情 SSE：按需连接，仅推送该 Bot 的实时流式输出与任务状态变更
PATCH/api/bots/:botId更新 Bot 设置（名称、指令、外观、权限、双层模型、工作项目）；切换项目时若忙碌返回 409 BOT_BUSY
POST/api/bots/:botId/visit记录 lastVisitedAt，消除该 Bot 侧栏未读完成/失败提示点
POST/api/bots/:botId/archive归档或取消归档 Bot { archived: boolean }
DELETE/api/bots/:botId删除 Bot；若存在未合并 Worktree 且未传 forceCleanupWorktrees: true 则返回 409 UNMERGED_WORKTREES
POST/api/bots/:botId/messages{ requestId, input }；幂等入队 user_chat Trigger 返回 202；绑定项目丢失返回 409 BOT_PROJECT_UNAVAILABLE
POST/api/bots/:botId/cancel取消该 Bot 当前 Router 生成（不影响已派发 Worker）
POST/api/bots/:botId/approvals/:approvalId{ taskId, allow }；审批该 Bot 下 Worker 的待确认命令
GET / POST/api/bots/:botId/tasks/:taskId/{session,diff,steer,cancel,apply,discard}查看单 Worker 实时会话、Diff、发送 Steer 纠偏、停止、安全预检合并回原仓或清理 Worktree

10安全底线、Phase 1 实施批次与演进路线

不可妥协的安全与稳定性底线：
  1. 严格工具与作用域隔离：Router 无底层文件/Shell 工具；Worker 强绑定目标 projectId 并受宿主 permission-policy.ts 裁决；所有 /api/bots/:botId/* 接口强校验资源归属关系（防止跨 Bot 越权操作任务或审批）。
  2. 零命令注入与零静默覆写：所有 git 调用走 argv 数组；Worktree 改动必须用户显式触发 apply 且预检无冲突才写回主仓，冲突保持原仓一字节不改。
  3. 进程重启与删除零数据丢失：重启时未完成任务统一转 interrupted 并保留 Worktree；删除 Bot 前若存在未合并 Worktree 强制二次确认；所有配置接口绝不暴露明文 API Key。
  4. Phase 2 记忆安全前置红线：后台 Worker 面对不可信仓库与网页内容，架构上严禁挂载 bot_remember / bot_forget，所有持久记忆必须经 Router 审核或用户显式确认。

Phase 1 验收门槛

  • 侧栏项目列表之上呈现独立 Bots 分区（支持展开/折叠、拖拽排序、72px 图标轨展示与状态聚合），新建 2 个分别绑定不同项目的 Bot 后，各自拥有独立永久对话且不污染普通项目会话列表。
  • 在任意 Bot 对话中连发 2 个写任务，底层自动在绑定项目的 Git 仓库中创建 2 个独立 Worktree（alphacode/bot/<shortId>）并行执行，主输入框全程无阻塞；完成后可在右侧抽屉查看实时轨迹、发送 steer 纠偏、预览 Diff 并安全合并或清理。
  • 为单个 Bot 分别配置独立 Router/Worker 模型（或配成相同模型、或继承全局默认），切换 Router 模型不丢失永久对话历史；在空闲时切换 Bot 绑定项目后对话保留，且旧项目的未合并 Worktree 仍正确合回原项目；忙碌时切换项目返回明确拒绝提示。
  • 后台 Worker 触发命令审批时，侧栏对应 Bot 立即亮起审批徽标，进入该 Bot 对话即可一键允许/拒绝；原有普通项目会话与多会话画布功能零回归。
  • 全仓 bun run build、bun run typecheck、bun run lint、bun run test 与桌面离线集成测试全部通过。
