Revision 03 / One naming convention.

创建统一 createX。
静态定义保持直接。

沿用已认可的 schema 定义与微内核设计。本轮统一创建 API：工厂使用 createX，静态配置直接声明对象，执行方法使用明确的动作动词。

00 / NAMING CONVENTION

名字直接说明：创建、定义，还是执行

上一版的参数定义保持不变。工具创建函数统一为 createTool；tools 仍是 Agent 配置中的工具集合字段。

import { z } from 'zod';
import { createAgent, createTool } from '@alpha/adk/standard';

const getOrder = createTool({
  name: 'get_order',
  description: '查询订单状态',
  input: z.strictObject({ id: z.string().min(1).describe('订单号') }),
  async execute({ id }, { signal }) {
    return JSON.stringify(await orders.get(id, { signal }));
  },
});

const agent = await createAgent({
  model,
  instructions: '先查询订单，再回答。',
  tools: [getOrder],
});

model 与 orders 来自应用。ADK API 为设计草案；schema 的类型推导、校验和转换沿用 v2。

类别统一规则例子
创建对象或能力create + 返回对象的含义；不混用裸名、defineX、makeXcreateAgent、createTool、createToolLoop、createModelBridge
创建带参数的插件create + 能力名 + PlugincreateAuthorizationPlugin(policy)、createTracePlugin(exporter)
静态定义直接声明对象；需要校验时使用 satisfies，不增加身份包装函数const auditPlugin = { ... } satisfies Plugin
执行、查询、注册、释放使用准确动作动词；不是创建就不加 createprompt、callModel、callTool、subscribe、addTool、close
类型与配置字段类型使用 PascalCase 名词，字段使用名词；集合保留复数Agent、Tool、Plugin；model、input、tools、plugins
工厂必须有真实职责：createTool 负责 schema 转换、运行时校验绑定与规范化；createAgent 负责组装和生命周期。仅为类型检查返回原对象的包装不引入 createPlugin / definePlugin，静态对象直接 satisfies Plugin。
静态插件的写法
import type { Plugin } from '@alpha/adk/core';

// onAgentEvent 是应用提供的观察函数。
const auditPlugin = {
  id: 'app.audit',
  apiVersion: 1,
  setup(api) {
    api.observe(onAgentEvent);
  },
} satisfies Plugin;

// 需要参数、独立状态或资源时，再用 createXPlugin(...) 工厂。
// 静态对象本身可含方法；关键是声明阶段无需工厂组装或资源初始化。
本轮 API 改名清单
  • tool → createTool；toolLoop → createToolLoop。
  • bridge → createModelBridge（应用侧模型适配器工厂）。
  • orderTools / authorizeTools / retrievalContext / traceObserver / mcpTools → 对应 createXPlugin。
  • 公开 Agent class 改为 Agent 接口，core 同样通过 createAgent 创建；实现可在内部使用 class。
  • Driver 的 model() / tool(id) 明确为 callModel() / callTool(id)，避免把执行误读为定义。

这些命名更新覆盖 API 示例、类型签名、插件组装预览与评审清单。schema、执行约束和依赖方向不变。查看 v2。

01 / RESEARCH

借鉴边界，不搬运框架

框架研究核对时间：2026-11-03；schema 标准补充核对时间：2026-11-04。比较的是公开的抽象与扩展机制，不做缺乏实测的体积、性能或星级排名。语言与运行语义不同，API 不直接移植。

Agent 框架机制比较，Alpha 取舍为设计推断
框架 / 范围已核对的实现机制Alpha 借鉴点 · 建议边界与代价 · 判断
Pi AgentTypeScript / agent-core 与 coding-agent有状态 Agent、独立 loop、事件流；消息转换与上下文变换分离。完整 Extension API 位于 coding-agent 层。[1–3]以 Agent 为入口；模型上下文是历史的投影；把应用扩展宿主放在上层。Pi core 本身依赖 pi-ai；其当前 loop 已有更多策略与 hook。借鉴分层，不声称原样复制即可得到零依赖内核。
Google ADK以 Python 插件语义为主Plugin 在 Runner / App 范围拦截；Agent callback 是局部配置。插件优先，部分非空返回值会跳过后续局部回调。[4]统一扩展生命周期，明确 scope、排序、短路和失败规则。不照搬多层 callback 优先级；Alpha 首版合并为一条有序管线，避免行为藏在返回值中。不同语言版本不假设一致。
LangGraphPython 文档 / 图运行时以共享状态、节点、边组织执行；checkpointer 保存线程图状态，store 保存跨线程数据。[5–6]区分对话历史、长时记忆、执行检查点。需要图编排时在外层组合 Agent。持久恢复需要调度与副作用协议，无法只靠“存一下消息”补齐；不将图调度器塞进首版内核。
LangChainPython / middlewaremiddleware 包装或介入模型与工具步骤；这些 hook 运行在 create_agent 返回的 LangGraph 内。[7]在调用边界建立上下文、策略、观察扩展点。不一开始暴露可任意多次调用 next 的万能中间件；重试会放大副作用与预算语义。
Pydantic AIPython / typed dependencies运行时传入 deps，通过泛型 RunContext 供工具与指令函数访问，支持测试替换。[8]应用上下文显式、类型化注入；上下文和模型消息分离。借鉴类型边界，不将 DI 容器、Python 类型系统或某个 schema 库写进内核。
MastraTypeScript / processorsAgent 组合模型与工具；input / output processors 在消息处理阶段变换、验证或控制内容。[9–10]便利入口与能力组合；将上下文变换做成明确流水线。全栈产品能力不等于内核职责。存储、Studio、工作流和部署层保持可选。

Pi 的关键启发，以及我们刻意不照搬的部分

Pi 的 Agent 状态、底层 loop 和 coding-agent 扩展属于不同层；这是本方案最主要的结构参考。源码还明确提供模型消息转换、上下文变换和工具调用拦截。[1–3]

Alpha 进一步把默认 loop 变成可替换模块，同时保留一个小型调用网关，保证替换 loop 后工具参数校验和取消约束仍存在。这是本方案的设计推断，并非 Pi 原有架构的逐项复刻。目录发现、TUI、slash command、热重载均属于更上层产品。

02 / BOUNDARY

小内核，明确的权责

点击各层查看职责。首版可同包分目录，以 exports 与静态依赖检查约束；包数量不是微内核的证明。

应用 → 预设 / 插件 → 内核公开契约
内核 ↛ 插件实现 / Provider / Node I/O
能力留在内核的机制插件 / 外层实现的策略
执行算法Driver 契约；run 状态；模型与工具调用边界默认 createToolLoop、固定单步、其他对话执行策略
模型ModelPort；流完成验证；终态与消息配对Provider 桥接、路由、协议参数；重试需独立契约
工具名称唯一；调用已编译的校验器；已确认调用 ID；结果提交具体工具、schema 库、授权规则、沙箱、MCP
上下文只读历史；受控投影 hook；投影后配对校验RAG、裁剪、摘要、skills、记忆召回
停止与预算AbortSignal；每次调用前原子计数；统一终态次数与时限配置、费用估算、业务停止条件
观察与持久化有序事件、只读快照、错误隔离；无默认存储trace exporter、日志、显式 session 保存 / 加载
内核准入测试：移除这个机制后，任意 Agent 是否会失去一致性或可组合性？如果只是某个产品少了一项功能，它应留在插件层。新增插件不得要求向 core 写 if (pluginName === ...)。

轻量的可验证定义

  • core 运行时第三方依赖目标为 0；不导入 Provider、Node 文件系统、MCP、数据库或 schema 库。
  • 仅导入 /core 时，不加载默认 loop 与插件宿主。
  • 两种执行策略、两种模型适配共享公开契约，core 无修改。
  • bundle 体积、冷启动、事件开销在 POC 后给实测；本稿不编造 KB 或毫秒目标。

扩展的实际边界

替换 loop 仍要遵循“对话消息 + 模型 / 工具调用”的 Agent 语义。任意分布式工作流不强行塞进 Driver；可在外层调用多个 Agent。

进程内插件是受信任代码。网关约束框架 API，不是安全隔离；恶意插件仍可自己联网。进程隔离由独立执行适配器与部署环境承担。

03 / COMPOSITION

卸掉插件，看看还剩什么

这是组装契约的本地演示。必需端口缺失时启动失败；选上功能只展示拟议配置，不代表功能已实现。

所有组合的 core 职责相同。无工具的 Agent 仍可对话；没有策略插件时，仅执行内核校验，不自动产生业务授权。

三类扩展点，不引入万能服务定位器

形态用途冲突与组合
单值端口Driver、ModelPort每个 Agent 恰好一个。直接配置与插件重复提供均报错；默认 loop 仅在没有显式提供时补上。
有序管线beforeModel、authorizeTool、mapToolResult注册顺序执行；变换依次传递；授权遇 deny 停止且不可被后续 allow 翻转。
集合 / 观察者工具注册、事件订阅工具名唯一，重复失败；观察者异常隔离。观察者不能阻止工具或持久化关键提交。
插件生命周期：显式安装、冻结注册、逆序清理
  1. 检查清单：插件 ID 唯一、apiVersion 支持，requires 引用已列在前面的插件；缺失、循环或向后依赖启动失败。不自动下载依赖、不隐式重排。
  2. setup：同步注册到临时表，无 I/O；任何名称或单值端口冲突使组装整体失败。随后冻结所有注册项。
  3. start：按清单顺序等待异步资源启动。失败时清理所有已进入 start 的插件，包含失败的那个，按逆序 dispose；清理错误聚合报告。
  4. 运行：插件实例按 Agent 创建；可显式共享外部客户端，但作者负责共享可变状态。同一 Agent 单 run，多个 Agent 可并发。
  5. close：拒绝新 prompt，取消活跃 run，等待收束后逆序 dispose；一次失败不阻断其他清理，重复 close 返回同一结果。

首版不做动态卸载、热更新、目录扫描、插件市场、任意字符串服务注册。资源型插件的 dispose 必须能处理部分启动；setup 不得持有资源。

04 / API PROPOSAL

常用 API 保持短，扩展契约单独看

下列接口是统一命名后的 TypeScript 设计摘录，省略部分辅助类型；尚未编译、发布或实现。包子路径也为拟议结构。应用依赖注入对象在示例中明确标注。

开发者用法

必须先稳定的运行语义
对象 / 动作明确约定
Agent / promptAgent 持有跨轮消息，单实例只允许一个活跃 run。core 创建配置错误同步抛出，预设创建错误通过 Promise rejection 返回；prompt 的 busy / closed / 输入错误以 Promise rejection 返回；启动后的执行故障通过 RunResult 表达。身份不同的用户必须使用不同实例。
状态快照数组、普通数据返回只读副本；model、工具实现和 appContext 不在公开快照中。消息内容仍可能敏感。运行中的重配或 replaceMessages 报 AGENT_BUSY。
模型流 / 消息提交delta 是暂定文本；流正常结束且恰好一个 finish 才提交 assistant。整个工具调用列表先验 ID 与结构；只有 tool_calls 终态可进入工具执行。拒答、截断、unknown 不执行工具。
调用网关Driver 只能通过 ctx.model / ctx.tool 调用。网关提交已验证消息、分配 run 内递增 seq，缓存本 run 已执行 callId 的结果；重复请求不重复执行。该去重不跨崩溃、不保证外部 exactly-once。
事件 / 流压力subscribe 同步通知、禁止阻塞 I/O；返回值不参与执行，抛错或异步拒绝隔离到 onObserverError。首版不内置无限 AsyncIterable 队列。UI / exporter 自管有界队列，可合并 delta；最终状态从 result / state 读取。
预算与取消maxModelCalls 在每次模型请求前原子扣减；不受 Driver 影响。达到限制返回 limited。timeout 发取消信号并禁止后续调用；取消为协作式，未收束的工具不能被宣称已停止。Agent 保持 cancelling 直至执行返回。
失败与副作用工具正常返回文本；异常默认使 run failed。首版不增加平行的工具错误返回 DSL，也不自动重试。after 阶段失败不能回滚副作用；结果未知时标记 history blocked，禁止直接再次 prompt。
Hooks 的顺序、可变性与错误处理
  1. beforeModel：按注册顺序传递消息投影，可裁剪 / 增补；不得改变 Agent 历史。网关重新验证 assistant / toolResult 配对。异常使 run failed。
  2. authorizeTool：工具查找与 schema 校验后、副作用前，参数为规范化只读值。不得改名或改参；首个 deny 返回安全 denied 工具结果。抛错终止 run，工具不执行。
  3. mapToolResult：允许变换回传模型的文本；不能改 callId、执行事实或取消 / 错误状态。异常时记录“已执行但结果处理失败”，不再次执行工具。
  4. observe：接收事实；不能短路、变换、授权或承诺可靠落盘。

直接 hooks 先注册，然后按 plugins 数组顺序注册。两者走同一条管线；没有隐式“全局 callback 高于局部 callback”。插件作者应声明顺序依赖。授权不是任意 around middleware，避免策略被替换结果或再次 next 绕过。

取消后的历史修复与恢复边界

用户消息在 run 开始时提交；未完成的模型 delta 不进正式历史。已确认的 assistant 工具批次中，完成的结果保留，未开始的调用补 not_executed 结果。对于已开始但执行结果无法确定的工具，补 outcome_unknown，并将 historyStatus 标为 blocked。

blocked 不能直接续问或自动重放。应用核对外部系统后，通过空闲态 replaceMessages(reconciled) 提供配对完整的新历史；该 API 不替应用证明业务副作用。持久恢复、steer/follow-up、暂停审批和多分支历史需要后续单独设计。

用失败场景检验抽象

    06 / SPIKE PLAN

    评审后，用最小实验淘汰坏抽象

    本轮统一 API 命名，沿用前两版的研究与执行契约。下列框架实施门槛尚未完成；本轮仅补充 schema 独立机制验证；不以“文档能展示”代替“框架能运行”。

    本轮已验证：仓库现有 Zod 4.6.7 可通过标准接口导出输入 JSON Schema，并拒绝错误类型、空订单号及额外字段。拟议 createTool 声明的严格 TypeScript 检查确认 id 推导为 string，错误参数类型与不匹配的工具上下文被拒绝。仅验证 schema 机制与声明，不代表 ADK 已实现。
    实验验证方式通过条件失败后的调整
    S1 / 单 schema 开发路径schema 类型推导、JSON Schema 转换与校验；再用 fake ModelPort 跑两轮 prompt无需手写输入类型 / parse；不支持的转换明确报错；core 无 schema 库依赖删减入口概念，先修 Developer API
    S2 / 循环可替换默认 createToolLoop 与单模型调用 Driver 使用同一 Agent不修改 core；两者都不能绕过预算、消息校验与取消修正端口粒度，不加入特定 Driver 分支
    S3 / 插件组合工具、授权、上下文、trace 四插件；冲突、依赖缺失、start 部分失败确定性顺序；deny 不翻转；资源逆序释放；无运行中注册简化 hook / 生命周期；不增加全局可变注册表
    S4 / Provider 桥接对本地 LanguageModel 做类型与模拟流契约测试，随后受控真实服务验证不双执行 tool-call；finish、取消、拒答、截断、Anthropic continuation、Responses 续接均覆盖明确不支持的协议组合并显式失败
    S5 / 异常收束六个推演场景 + busy、预算耗尽、慢观察者、忽略 signal 的工具终态唯一；状态不串 run；未知副作用阻断续接；无无界事件队列收紧契约；需要强终止时独立进程执行
    S6 / 轻量审计检查依赖图、exports；core 单独 bundle；记录空载与插件启用时开销core 无可选能力运行时依赖；公开入口可独立导入；记录可复现实测拆分实现依赖；根据证据设置体积与延迟门槛

    建议首轮 POC 范围

    Agent + 状态、ModelPort、Tool、Driver 网关、三类 hooks、插件组装、createToolLoop、现有 Provider bridge。存储仅验证显式外层 CAS 接口；不接入完整数据库。

    保持在后续阶段

    MCP 实际客户端、RAG 实现、持久 checkpoint、多 Agent 调度、热重载、审批恢复、自动重试、多模态、远程沙箱。现阶段检验扩展接缝，不一次性建设全部生态。
