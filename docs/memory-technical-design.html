Alpha Memory 模块技术方案设计

收敛掉重型向量库、知识图谱等泛化框架，只向两个最成功的实战 Coding Agent —— Claude Code（Anthropic）与 OpenAI Codex CLI 取经。两家不约而同地选择了「本地 Markdown 文件作为记忆本体 + 极简常驻索引 + 后台异步抽取与整固 + 零向量库起步」。本方案融合两家精华，贴合 Alpha 现有的 AGENTS.md、bun:sqlite、@alpha/adk-context 与 Multi-Bot Super-agent 架构，给出极简、高可靠、零外置依赖的落地设计。

状态：聚焦评审稿 v2.0（暂不写代码） 对标标杆：Claude Code (Auto Memory + Auto-Dream) & OpenAI Codex (Stage 1 / Stage 2 Pipeline) 拟新增包：@alpha/adk-memory（layer:memory） 100% 离线可读 HTML + 可交互原型

01Claude Code vs OpenAI Codex 记忆实现深度拆解

很有意思的一个工程共识：Claude Code 和 OpenAI Codex 都没有引入 Qdrant、Neo4j 或复杂多跳图检索。在真实的软件工程场景里，代码仓本身就是最好的结构化真相源，Memory 要解决的是「代码里查不到的上下文：用户偏好、历史纠正、项目隐性约束与踩坑经验」。

标杆 A · Anthropic Claude Code 指针索引 MEMORY.md + 主题文件 + extractMemories + autoDream

把记忆组织成一个项目级本地目录 ~/.claude/projects/<project-hash>/memory/（同一 Git 仓的多个 Worktree 共享同一份记忆）。
• 常驻层：只加载 MEMORY.md 前 200 行（约 25KB），里面只放“一句话指针链接”，超行静默截断。
• 详情层：独立主题文件 *.md，带 YAML frontmatter（name / description / type），严格分 4 类：user / feedback / project / reference，明令禁止记录可从代码/git 推导的事实。
• 按需召回：靠 MEMORY.md 指针 + findRelevantMemories 扫描 frontmatter 按需读文件；且强调“行动前以当前代码为准复核旧记忆”。
• 写入与整理：既允许对话中直接写，也在轮次结束时由轻量后台子 Agent（extractMemories，上限 5 轮，若主 Agent 本轮已写则跳过防冲突）补漏；长期靠 autoDream（满足 24h + 5 会话 + lockfile 三道门控）分 Orient → Gather → Consolidate → Prune 四步清理腐烂记忆。

标杆 B · OpenAI Codex CLI SQLite 调度双阶段流水线（Stage 1 抽取 → Stage 2 整固）+ 生成态手册

把长期记忆视为一套完全异步的离线编译流水线（memories = true），把状态放在 ~/.codex/memories/ + 嵌入式 SQLite（jobs 与 stage1_outputs 表），绝不阻塞用户当前交互热路径。
• 静态层 vs 动态层：AGENTS.md（全局 + 仓根目录向下合并，硬限 32 KiB）归人类手工维护；~/.codex/memories/ 明确划为机器生成的只读产物。
• Stage 1（按会话抽取）：老会话闲置后，后台通过 SQLite jobs 表租约认领未处理会话，先清洗密钥与环境变量，抽取为单会话 rollout_summaries/<slug>.md 与 stage1_outputs 原始记录。
• Stage 2（全局整固）：独立冷却与水位线控制，按时效与价值综合排序，把零散 raw 记录提炼成三份层次清晰的文件：memory_summary.md（极简导航，首轮注入 Prompt）、MEMORY.md（完整经验手册）与 raw_memories.md，并用本地 .git 追踪变更。

03存储设计：Markdown 主题文件 × 极简 SQLite 调度库

我们的分工非常克制：人需要看到和修改的东西（记忆正文）一律用明文 Markdown 文件（Claude Code 路线）；机器需要防并发冲突、记断点水位线和做快速过滤的东西一律用 3 张极简 SQLite 表（Codex 路线）。删掉数据库文件也不会丢失任何一条记忆，重新扫描目录即可自动重建索引。

3.2 主题文件格式与四类分类法（直接对标 Claude Code）

每条主题记忆就是一个独立的 topics/<slug>.md，头部带极简 YAML Frontmatter，仅保留 4 类高价值记忆类型（并明确排斥易腐烂的代码现状）：

示例 · topics/feedback-bun-tests.md 
---
name: 离线单测与设计先行规范
description: 复杂架构先出 HTML 方案；单测用 bun:test 离线夹具，不自动请求付费模型
type: feedback
owner: user
updated_at: 2026-11-27
---

复杂模块改动前先输出 HTML 设计文档评审，确认后再写代码。
自动化测试默认使用 bun:test + 离线 HTTP/模型夹具；真实端点只在显式 live 脚本中运行。

**Why:** 避免未对齐架构直接返工，且防止 CI/本地单测产生意外模型费用。
**How to apply:** 每次新增 packages/* 模块或跨层改造时先给方案。
示例 · MEMORY.md（常驻指针索引，严限 ≤ 200 行）

3.3 极简 SQLite 调度库（sessions.db.memory.db · 仅 3 张表）

直接借鉴 OpenAI Codex 的 jobs + stage1_outputs 设计，解决 Windows 跨进程文件锁痛点，同时提供派生 FTS5 索引加速 UI/Agent 搜索：

-- PRAGMA journal_mode = WAL; PRAGMA busy_timeout = 5000;

-- 1. 后台任务租约与水位线（Codex 风格：取代脆弱的文件系统 lockfile）
CREATE TABLE IF NOT EXISTS memory_jobs (
  job_key TEXT PRIMARY KEY,              -- 例如 "stage1:session:<sid>" 或 "stage2:dream:project:<pid>"
  kind TEXT NOT NULL,                    -- 'stage1_extract' | 'stage2_dream'
  scope_key TEXT NOT NULL,               -- 'user:default' | 'project:<id>' | 'bot:<id>'
  status TEXT NOT NULL,                  -- 'idle' | 'running' | 'done' | 'failed'
  lease_owner TEXT,                      -- 当前持有锁的进程/worker 实例 ID
  lease_expires_at TEXT,                 -- 租约超时自动释放，防止进程崩溃死锁
  watermark TEXT,                        -- 已处理到的 session revision / 时间戳
  retry_count INTEGER NOT NULL DEFAULT 0,
  last_run_at TEXT,
  last_error TEXT,
  updated_at TEXT NOT NULL
);

-- 2. Stage 1 原始抽取缓存（幂等：同一会话未新增轮次绝不重复抽）
CREATE TABLE IF NOT EXISTS stage1_outputs (
  session_key TEXT PRIMARY KEY,          -- "<namespace>:<sessionId>"
  scope_key TEXT NOT NULL,
  session_revision INTEGER NOT NULL,     -- 对齐 sessions.db 归档 revision
  rollout_path TEXT NOT NULL,            -- 相对路径 rollouts/<slug>.md
  raw_takeaways TEXT NOT NULL,           -- 脱敏后的结构化要点（供 Stage 2 整固消费）
  skipped_reason TEXT,                   -- 例如 'main_agent_already_wrote' | 'no_durable_signal'
  consumed_by_dream_at TEXT,             -- NULL = 待 Stage 2 消费
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_stage1_pending ON stage1_outputs(scope_key, consumed_by_dream_at);

-- 3. Markdown 文件派生元数据与 FTS5 索引（纯缓存：删库后扫磁盘 100% 自动重建）
CREATE TABLE IF NOT EXISTS memory_files (
  path TEXT PRIMARY KEY,                 -- 相对 ~/.alphacode/memory/ 路径
  scope_key TEXT NOT NULL,
  kind TEXT NOT NULL,                    -- 'index' | 'topic' | 'rollout' | 'pending'
  mem_type TEXT,                         -- 'user' | 'feedback' | 'project' | 'reference'
  owner TEXT NOT NULL DEFAULT 'agent',   -- 'user' (锁定禁改) | 'agent'
  name TEXT NOT NULL,
  description TEXT NOT NULL,
  content_sha256 TEXT NOT NULL,
  mtime_ms INTEGER NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE VIRTUAL TABLE IF NOT EXISTS memory_files_fts USING fts5(
  path UNINDEXED,
  scope_key UNINDEXED,
  tokens_lex,                            -- 英文 / 标识符 / 路径
  tokens_cjk,                            -- 中文 2-gram（零依赖支持中文检索）
  tokenize = 'unicode61 remove_diacritics 2'
);

04双阶段后台流水线：Stage 1 抽取 × Stage 2 Auto-Dream

将 Claude Code 的在线即时写 + 四步 Auto-Dream 与 OpenAI Codex 的双阶段异步抽取/整固 拼成一条极度清晰的工作流：用户显式指令秒级响应，隐式学习与整理全部放到后台，零阻塞交互热路径。

流程图 2 · 在线快路径 + Stage 1 异步抽取 + Stage 2 Auto-Dream 四步整固
零热路径延迟 · 主 Agent 本轮已写则跳过防竞态 · 密钥先脱敏再落盘 · 整固前自动快照

为什么同时吸收两家，而不是二选一？

  • 只学 Codex 的短板：Codex 的记忆完全靠离线后台产出，当用户在对话里明确说“以后不要用 pnpm，全用 bun”时，如果立刻新开一个会话，可能还没等到 Stage 2 整固，体验上会觉得“刚让你记住怎么转头就忘”。加入 Claude Code 的在线快路径正好补齐即时反馈！
  • 只学 Claude Code 的短板：Claude Code 用文件系统 lockfile 协调并发，在 Windows 桌面端 + 多 Bot 并发场景容易出现脏锁或竞态；且缺少单会话 rollout_summaries 中间层，每次 Dream 要重新扫描长会话记录。引入 Codex 的 SQLite memory_jobs 租约 + stage1_outputs 中间沉淀，让整固成本极低且绝对幂等！

05Prompt 注入、零向量库召回与安全防火墙

架构图 3 · 会话首轮注入、按需深读与 Multi-Bot 写防火墙
复用 beforeModel · 首轮注入后会话期内冻结（保住 KV Cache & 检查点）· Worker 严格只读

为什么首期不做 Embedding / 向量库？

  • Claude Code 与 Codex 的实战证明：单项目沉淀的高质量主题记忆通常只有 15–80 个文件，总索引不到 200 行。把 200 行高信噪比指针直接给大模型看，模型自己选读哪 1–2 个主题文件的准确率，远高于盲目切块做 Top-K 向量相似匹配！
  • 辅助 FTS5 兜底：当 rollouts/ 历史沉淀超过几百条时，memory_search 直接查本地 memory_files_fts（内置英文标识符 + 中文 2-gram），毫秒级零延迟、零 API 费用、桌面端安装包零膨胀。
  • 留好扩展口：如果未来单个用户历史滚到数千条且真的出现语义查不到的问题，只需给 MemoryStore.search() 挂一个可选检索后端即可，上层文件格式与工具契约完全不变。

06极简开关设计（零独立 UI）与磁盘文件演练

与 Claude Code 和 OpenAI Codex CLI 一致：我们不需要单独开发一套 Memory 管理界面或内置 Markdown 编辑器。记忆本身是本地明文文件（~/.alphacode/memory/），需要查看或修改时直接用系统编辑器打开，或者直接在对话里对 Agent 说“记住/忘掉…”即可。

已收敛产品形态：零独立 Memory 页面，只做「启用开关」
1. 全局总开关：复用现有 Settings → 通用设置，增加一行简洁开关（默认 关闭 / opt-in，与 Codex memories = true 一致），持久化到 ~/.alphacode/config.yaml 的 memory.enabled。
2. 单 Bot 独立开关（可选覆盖）：直接复用 bots.db 已经预留的 bots.memory_mode（'alphacode' | 'off'），在 Bot 设置页 提供一个开关，允许对特定 Bot 单独关闭记忆。
3. CLI 零鼠标控制：通过 config.yaml 或 /remember、/memory、/memory dream 即可完成全部操作。

7.2 核心 TypeScript 契约与 3 个极简工具

export type MemoryScopeType = "user" | "project" | "bot";
export type MemoryType = "user" | "feedback" | "project" | "reference";
export type MemoryOwner = "user" | "agent";

export interface MemoryScope {
  readonly type: MemoryScopeType;
  readonly id: string; // "default" | projectId | botId
}

export interface MemoryTopic {
  readonly scope: MemoryScope;
  readonly slug: string;          // 对应 topics/<slug>.md
  readonly name: string;
  readonly description: string;   // 一句话摘要，同时用于 MEMORY.md 指针与检索
  readonly type: MemoryType;
  readonly owner: MemoryOwner;    // "user" 时禁止 Agent 覆写/删除
  readonly body: string;
  readonly updatedAt: string;
}

export interface MemoryPluginOptions {
  readonly store: MemoryStore;
  readonly readScopes: readonly MemoryScope[];      // 普通会话: [user, project]；Bot: [user, project, bot]
  readonly writeScope?: MemoryScope;                // 缺省或 writeMode="readonly" 不挂写工具
  readonly writeMode: "direct" | "propose_only" | "readonly";
  readonly maxIndexLines?: number;                  // 默认 200（对齐 Claude Code）
  readonly maxIndexBytes?: number;                  // 默认 12 * 1024
}

// 仅向模型暴露 3 个极简工具（Worker 仅获得前 2 个 + 可选 propose）：
// 1. memory_read({ scope, path })                  → 按需读 topics/*.md 或 rollouts/*.md
// 2. memory_search({ query, scopes?, limit? })     → 走 FTS5 派生缓存搜标题/摘要/正文
// 3. memory_write({ scope, slug, name, description, type, body, action?: "upsert" | "delete" })
