C1 的最小闭环

读代码 → 修改 → 运行验证 → 报告

默认装配工作区工具和根目录项目指令。普通修复使用一个 Agent；无需先引入 Planner / Executor / Reviewer 多 Agent 分工。

提供可嵌入 API 和最小 headless 示例。复杂 TUI、IDE 和多客户端服务放在宿主层。

资源谁创建谁关闭

core 增加通用运行边界，保持唯一 Loop

api.provideRunBoundary(boundary) 至多允许一个贡献者。prepare 在模型 / 工具前被等待，可受控恢复完整正式历史，完成准入，或返回旧结果跳过执行；complete 在运行收束后被等待，得到真实终态和消息快照。

history.restore 仅在 prepare 阶段有效。安装边界后，外部 replaceMessages 返回 HISTORY_MANAGED。core 不导入 Session、SQLite 或 Coding；observer 仍只作观察，不承担可靠存储。

正常结果、保存失败与重复请求

agent.prompt() 返回 RunResult；session.state.persistence 表示 saved / pending。保存未确认时保留执行结果并拒绝下一次 prompt；调用 session.flush 只补写原候选。run.end 早于保存确认，不能据此宣布归档成功。

requestId 可省略，为新请求生成 ID；跨进程 / 网络重试应显式保留原 ID 和输入。同 ID 同输入直接返回旧结果，不重放模型、工具或事件；同 ID 不同输入拒绝。命中旧结果不强制载入 Agent 历史，下一次真实执行前才恢复。

如果 complete 意外抛错，core 保留真实 RunResult，将 boundaryStatus 标为 failed 并禁止后续执行。正常存储失败由 Session 表达为 unsaved，允许原句柄 flush；不是把存储错误伪装成模型失败。

关闭、重开和数据兼容

一个 Session 句柄同时只绑定一个 Agent，一个插件实例只能装配一次。Session / Manager 绑定期间 close 返回 SESSION_BOUND；宿主先关闭 Agent，再关闭数据句柄，最后关闭借用的 Store。

Agent 关闭等待在途工作，并在插件释放时尝试补写一次、解除绑定。补写失败也保留原 Session 候选，可以在 Agent 已关闭后继续 flush；Session / Manager 关闭未保存句柄时同样保留可重试状态。

重开使用 sessions.openSession(savedId)，随后创建新插件和 Agent。已有 formatVersion=1 的 Memory / SQLite 数据兼容；S1 的 createAgent 配置、session.prompt / abort、转发 Agent 事件不再提供。

验证记录：core 83 项、Session 51 项、Provider 25 项，共 159 项测试通过；构建、类型检查和 lint 通过。本机真实模型完成 3 次模型调用、1 次工具执行，SQLite 关闭重开后成功恢复，重复请求增加 0 次模型调用。

便捷工厂与显式装配如何保持等价？

createCodingAgent 组装 coding 系统指令、工作区插件、可选的项目指令插件和额外插件，最后调用现有 createAgent。返回对象仍满足原 Agent 契约：idle、空正式历史、普通 prompt / subscribe / abort / close。

便捷工厂建议将运行限额设为 24 次模型、64 次工具、180 秒总取消期限；其他 core 限额沿用现有值，显式 limits 可覆盖。显式装配若希望相同行为，应使用相同指令和限额。整体替换工作区能力时使用显式装配和自定义 core Plugin；C1 的内置工作区插件固定提供六个工具，暂不承诺逐个替换其私有计划逻辑。重复工具名 / plugin id 继续由 core 拒绝，插件注册在创建后冻结。

工作区适配器为什么需要“已知拒绝 / 已应用 / 未知”三种结果？

writeFile 的 rejected 只表示已证明没有发生目标变更；applied 需要确认目标版本；unknown 表示不能确认。领域工具把已知结果编码为字符串返回，只对 unknown 抛错，让现有 core 正确产生 outcome_unknown / blocked。

它是适配器作者的 I/O 契约，不是新增模型协议。readFile / listFiles / search 是受目录边界限制的只读操作；写文件与命令仅由独占租约提供。不同插件共享显式 Workspace 依赖，不通过全局服务注册器寻找彼此的私有状态。

为什么这里没有 approve(requestId)、resumeTask() 或热加载接口？

C1 的审批是 authorizeTool 内等待一次宿主回调，仍属于同一个在途 run。没有 durable pause，进程重启后不能凭审批结果重放工具。动态注册、审批恢复和远程会话协议需要后续单独设计，不能借 observer 暗中实现。

06 / EXECUTION CONTRACT

先准备具体操作，再授权，再执行

  1. 校验参数
  2. 生成执行计划
  3. 策略 / 宿主批准
  4. 再核对前置条件
  5. 执行并确认结果
  6. core 收束 / Session 保存

同一份计划贯穿审批和写入

工作区插件在 authorizeTool 中读取文件、核对 read 版本、计算唯一替换与 diff，生成冻结的计划。此阶段不创建临时文件、不运行命令。

预检发现可确认的冲突时缓存拒绝结果；若网关准入，execute 仅返回该结果，不写入、不请求一次无意义的修改批准。计划按 agentId / runId / assistantId / callId 绑定，digest 覆盖工作区、目标路径、参数、前置版本、命令与 shell。execute 使用这份计划，授权后不重新解释成另一项操作。

等待审批后目标内容发生变化，返回 FILE_CONFLICT，零写入；需要重新读取并形成新调用。

策略是可替换的静态对象

默认允许工作区内读取和普通文件修改；命令调用 ask，自定义工具 deny。宿主可以根据真实业务权限替换 policy，让已授权的操作自动进行。

ask 缺少 approve 回调就 deny。拒绝不会启动工具；审批等待时取消，由现有 core 收束。UI 展示具体 diff / 命令，不能只显示“允许工具？”

policy 或回调异常不能变成 allow；core 保留 HOOK_FAILED / 取消等既有语义。审批本身不写 Session 的第二套状态。

路径约束和审批不是 OS 沙箱。LocalWorkspace 的 isolation 必须如实报告 none。shell 中的脚本可以使用宿主权限与网络，工作区路径检查不能约束任意子进程。需要技术隔离时更换真正受限制的 Workspace 适配器；C1 不提供一个写着 sandbox=true 却没有系统保障的开关。
工程边界建议约定
路径工具只接受工作区相对路径；拒绝绝对路径、..、UNC / ADS 越界等输入。检查 canonical root、符号链接 / junction 及目标父目录，写入前复核。该检查不能宣称防住所有恶意并发替换。
并发写入工作区租约防止合作中的 Alpha Agent 并发；外部编辑器仍可能改文件。检查 hash 后同目录临时文件替换只能覆盖已观测的冲突窗口，不能把文件系统包装成跨进程、跨文件数据库 CAS。
Windows明确使用 PowerShell 7 / pwsh；运行隐藏窗口、固定工作目录、无交互 stdin。搜索使用 rg，不假定 grep / sed / Bash 存在。已实测跨进程独占锁、取消/超时回收 detached 子进程与孙进程，以及宿主死亡后的释放。
停止先请求停止，再终止并等待所拥有的进程树；不允许后台脱离进程。不能确认子树结束或写入结果时报告 unknown，不能提前释放租约，也不自动继续下一轮。
环境和项目文件使用显式最小环境与宿主追加值，不把父进程中的所有凭证继承给命令。项目指令是文本，不自动安装依赖、执行脚本或导入项目插件。
扩展信任进程内插件拥有宿主代码权限。authorizeTool 可以约束经网关的调用，不是对恶意插件的隔离。LSP / MCP 等后续扩展应继续声明 effect 与生命周期，不能绕开网关执行。
项目指令和长上下文如何接入？

C1 只加载根目录 AGENTS.md（或宿主显式配置的相对路径），在插件 start 阶段读取有界文本，beforeModel 为当前投影添加上下文，不修改正式历史和受保护工具批次。默认上限 32 KiB。缺文件视为空；读取失败或超限明确失败，不悄悄忽略。

目录级 AGENTS.md、Skills 发现、repo map、摘要放到 C1.1 / C2。指令在 Agent 生命周期内固定，更新后需关闭重建并由宿主维护 agentKey 的兼容版本。默认 coding 系统指令明确项目文本不能改变权限策略。

Session 选择完整轮次控制工作集，文件内容按需读取。Session 归档不是每次完整模型 prompt 的快照；项目指令等临时上下文若要逐次审计，应由独立记录能力补充，不宣称当前 S2 已具备这种审计。

文件修改成功后，Session 保存失败怎么办？

磁盘变更与 SessionStore 提交不在同一个事务里。保留 RunResult + persistence: pending，用原句柄 flush 只补写归档。不能再次执行编辑或命令，也不能以“保存失败”为理由还原用户工作区。

若进程已经丢失，SQLite 中可能只有 pending；沿用 S2 的 RECOVERY_REQUIRED。文件差异、对话归档和工具 checkpoint 是三种不同记录，C1 不假造 exactly-once 外部效果。

已落实的实现选择与边界
  • Windows：PowerShell 7 bridge 持有 FileShare.None OS 锁；CreateProcess suspended 后加入 Job Object 再恢复。跨进程抢锁与孙进程收束有真实测试。
  • 文件：严格 UTF-8、BOM/CRLF 保留、同目录临时文件 + rename / 独占 link；路径和版本重检，不宣称恶意外部并发下的原子 CAS 或 ACL 完整保留。
  • 搜索：rg 固定参数数组 + 字面匹配，先尊重 ignore，再由 minimatch 筛选 glob；原始输出上限 4 MiB。命令工具执行宿主批准的 shell 字符串。
  • schema：Coding 包使用现有 Zod 4 单 schema；core 无改动，仍只使用标准协议。根入口不加载 Node adapter 或 Session。

真实修复已通过 http://127.0.0.1:3425/v1 / codex/gpt-6.1-sol：5 次模型调用、2 次测试命令、1 次源码修改；测试从 exit 1 到 exit 0，测试文件未改。Session 原 Agent / 重新接入重放均为零新增副作用。
