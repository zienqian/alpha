# search 与 ast-grep 对比方案

日期：2026-11-13。状态：源码审查与 CLI pilot；尚未修改生产搜索，也未运行模型任务 A/B。

## 建议与待验证假设

保留 ripgrep 的文本搜索，试验新增 `search_code` 结构搜索。暂不把现有 `search(query)` 的字面语义替换为 AST pattern。

- ast-grep 用 Tree-sitter 解析语法结构，适合调用、声明、导入、嵌套关系和跨行代码；纯文本、文档、日志、错误字符串与文件枚举仍需文本工具。
- 结构搜索可能通过减少误命中、重复搜索和 `read_file` 节省整个任务的上下文。解析 AST 有额外成本，不能预设单次搜索比 rg 快。
- AST 命中可能包含整个函数或对象，默认 JSON 又包含 `text`、`lines`、range、metavariables；直接回传可能更费 token。
- AST 的语法匹配不等于类型、符号绑定或跨文件引用解析。导入别名、同名局部变量、调用链等任务必须单独验证，不能宣称替代 LSP。

上述能力与限制依据：[核心概念](https://ast-grep.github.io/advanced/core-concepts.html)、[能力比较](https://ast-grep.github.io/advanced/tool-comparison.html)、[JSON 格式](https://ast-grep.github.io/guide/tools/json.html)。速度与节省比例必须由本项目实验确定。

## 当前实现及对照的必要性

- `packages/coding-agent/src/tools/search.ts`：`search` 为 read 工具，参数 `path/query/glob/limit`，单行字面查询。
- `packages/coding-agent/src/search.ts`：`rg --fixed-strings --json --sort path`；默认 100 条，最多 1000 条，单文件不超过 1 MiB；原始输出保留 4 MiB。
- 搜索尊重 ignore，包含隐藏文件并排除 `.git`。`glob` 在 rg 输出之后通过 minimatch 过滤；代码注释明确说明，直接改成正向 `rg --glob` 会覆盖 ignore 行为。
- 等整个进程完成后才解析 JSON、检查匹配路径、应用 glob、截取结果。`limit=100` 不代表仅搜索到 100 条就结束。
- 本机 rg 15.2.0 的 `--help` 明确说明：`--sort` 强制单线程。移除它后必须在应用层恢复稳定排序；无序流直接取前 100 条会改变结果集合。
- `src/internal.ts` 的 `encode` 再按结果预算缩减数组；core 默认 `maxToolResultBytes=128 KiB`，宿主可以覆盖。比较必须使用相同实际预算。

所以需要分别验证搜索引擎、封装、输出格式三个因素，不能将缩短结果的收益全部归因于 AST。

## 实验分组

| 组 | 实现 | 回答的问题 |
| --- | --- | --- |
| A | 当前 search 与输出 | 真实基线 |
| B | rg + 候选文件预筛选、合适的并行/排序、紧凑输出 | 不换引擎能改善多少 |
| C | B + 独立 `search_code`，模型按任务选择 | AST 的增量收益，推荐候选 |
| D | AST-only | 替换的能力边界；文本/不支持语言的失败也须记入 |

B/C 使用同一输出协议、默认数量、字节预算、排序和文件访问语义。另做输出格式消融：原生行/节点片段、相同有界摘录、仅定位。仅定位对两种引擎都开放，之后增加的 `read_file` 开销照常计入。

CLI pilot 只覆盖 A 的命令形态、取消 rg 内部排序的对照、ast-grep 原型；它不是已经实现的 B/C。

## 第一层：检索基准

数据范围：coding-agent 小目录、本仓库、较大的固定真实仓库。扩展集覆盖 TS/TSX、JS、JSON、Markdown 和非支持语言。记录 commit、工作区差异、文件 hash、工具/语法版本、机器、线程数、磁盘与文件数量。

建立至少 40 个检索案例：12 个文本定位、16 个结构查询、8 个文本与结构混合、4 个空结果/错误输入。结构案例包括 `createTool` 调用、带泛型调用、跨行实参、特定对象属性、导入形式、try/catch 内调用；对抗样例包括注释、字符串、相似名称、同名绑定、别名、可选调用、语法错误和嵌套调用。

参考答案由人工/独立审查标注路径和区间，不用某个被测引擎的输出当 ground truth。明确任务是在找语法形态还是某个符号的实际引用。分开统计无上限召回率与预算内 recall@K，不能把截断或漏搜当成节省。

每组先预热，再交错重复 30 次；记录原始样本、p50/p95 和成对差值。线程实验包含默认策略和固定单线程。分别测：

1. 引擎：相同候选文件，进程启动至 stdout 结束；另记第一条有效匹配时间。
2. 工具：文件枚举、权限检查、glob、JSON 解析、排序、序列化后的完整延迟，以及峰值内存。
3. 输出：原始 IPC 字节、最终 toolResult 字节/token、有效/无效命中数、截断、错误和超时。

OS 热缓存、真正 OS 冷缓存、进程冷启动、AST 缓存是不同条件。未清空系统文件缓存的首次进程运行不能叫冷缓存测试。缓存优化另开组，并计入建索引时间、内存和文件修改失效成本。

## 第二层：Agent 任务评估

选择 40 个真实任务：12 个文本/配置定位、16 个结构定位或修改、8 个混合探索、4 个失败/回退。先在开发集调试工具说明，再冻结提示和规则，用独立评估集比较 A/B/C；D 先做能力验证。

同一模型版本、推理设置、系统提示、预算、机器和代码快照，每任务每组至少 3 次独立会话，交错运行。40 × 3 × 3 = 360 个任务运行，这是计划规模，尚未执行。每次重置代码；修改任务以最终 diff 和测试结果判分，纯定位任务按标注答案判分。

必须保留模型错误的 AST pattern、修正轮次、语法查看、回退、超时和失败；不允许只挑人工调好的 AST 命令与 Agent 自己的 rg 命令比较。保持其余工具可用性一致；记录 `run_command` 绕过搜索的行为，或者在一个明确标注的受限实验中对所有组同时禁用这种绕过。

核心指标：

| 指标 | 定义 |
| --- | --- |
| 任务成功率 | 正确完成数 / 全部任务数；失败不能从成本样本中消失 |
| 总输入与输出 token | 各模型调用 usage 之和，包含 schema、说明、参数、工具结果、读文件、修正与重复历史 |
| 上下文窗口占用 | 各调用请求的输入 token 最大值，以及去重后的新增检索内容 token；与累计输入分开报告 |
| 计费成本 | 有真实 usage/计价时单列；缓存输入折扣不等于上下文减少 |
| 完成延迟 | 用户请求至最终完成，p50/p95，连同搜索与模型耗时拆分 |
| 交互效率 | 搜索次数、read_file 次数、模型轮数、回退次数、无效命中比例 |

直接复用 `packages/adk-trace` 的 model/tool span、duration、`inputTokens/outputTokens`、`totalModelCalls`。目前暴露的 usage 没有缓存 token 明细；缺失时明确标为不可测，不能推算实际费用。离线 tokenizer 计数仅作为输出长度代理，不替代模型 usage。

汇总同时给出按任务类型的结果与整个评估集的配对结果。成功任务间的 token 对比需要单独列出，同时保留全体运行成本、失败数和超时，避免“更快失败”被误报为优化。报告置信区间；样本不足时扩大实验，不以小样本零差异证明等价。

## 候选接口与落地顺序

试验阶段保留 `search`，新增 read-only `search_code({ path?, language, pattern, glob?, limit?, output? })`。显式传 language/pattern，不依据一个普通字符串自动猜测用户想做字面还是结构搜索。第一版只做 pattern，复杂规则在确认需求后加入，避免一开始将完整 YAML DSL 放进工具 schema。

默认返回路径、起止行列和有界摘录，显式标记摘录/结果截断；完整节点按需读取。CLI 内部使用 `--json=stream`，不要将完整原生 JSON 直接给模型。AST 位置从零基转换成现有工具的一基行号；同一行多个 AST 节点应保留列或区间以免错误去重。

先用 CLI 复用当前进程生命周期、超时与取消能力；确认进程启动/重复解析占主要耗时后，再另测 `@ast-grep/napi` 的常驻解析/缓存，不预设 native API 一定更快。[官方性能提示](https://ast-grep.github.io/guide/api-usage/performance-tip.html)也建议减少跨语言调用并采用批量查询。

两种引擎共用候选文件策略，保留 ignore、hidden、1 MiB、路径和符号链接权限。自动加载项目自定义 native parser 关闭，结构搜索不开放 rewrite。搜索成功不获得 edit_file 的读取凭据。语言不支持、pattern 非法、二进制缺失和解析异常给出明确错误；合法零命中不能悄悄当作文本查询重试。模型可显式转回 `search`，其开销计入评估。

优化 rg 的候选文件过滤时，先取得遵守 ignore 的文件集合再应用 glob，避免直接正向 glob 改变现有边界。并行扫描 + 全局稳定排序不能无条件提前停止；若测试有序分批/流式提前终止，须验证结果前缀和截断标记与基线一致。

## 决策门槛（实验前约定，非已获收益）

- 兼容性硬门槛：文本语义、ignore、路径权限、排序、取消及截断契约通过；结构任务参考集没有新增未解释漏搜。
- 质量优先：总体成功率不低于基线；统计区间尚不能支持该判断时扩大样本，不直接全量切换。
- 优先采用 C 的候选信号：结构任务累计输入 token 中位数降低至少 25%，整个任务集降低至少 15%；完整任务 p95 延迟不恶化超过 10%。同时比较 C 相对 B，确认 AST 仍有增量收益。
- 如果收益主要来自 B 的输出/封装优化，先上线 B。若 C 只在少数结构任务有收益，将其保留为可选能力。
- 只有 D 在相同任务集和能力契约上也达标，才讨论全替换；不能因结构子集更好而删除文本搜索。

## 本次 pilot 的复现

依赖安装到系统临时目录，不改根 package.json、lockfile 或生产依赖。Windows x64 示例：

```powershell
$benchTools = Join-Path ([System.IO.Path]::GetTempPath()) 'alpha-search-eval-20261113'
npm install --prefix $benchTools --no-save --package-lock=false --ignore-scripts --no-audit --no-fund @ast-grep/cli@0.51.2 js-tiktoken@1.0.21
node scripts/bench-search.mjs --ast-grep "$benchTools\node_modules\@ast-grep\cli-win32-x64-msvc\ast-grep.exe" --tokenizer-root $benchTools --output docs/search-ast-grep-pilot.json
```

脚本要求 Node.js 20+、PATH 中的 rg；其他系统传入对应平台的 ast-grep 二进制路径。源码快照留在报告的 `methodology.snapshot` 临时目录，便于检查；报告包含文件 SHA-256、命令版本、工作区状态、全部时间样本和独立 fixture 答案。重新运行会创建新快照并覆盖指定报告。

计时仅为 CLI 加简化 JSON 适配器，未经过生产 searchFiles、真实权限检查与 ADK。当前环境的 PATH Bun 启动器不可运行，因此本次使用 Node 执行隔离脚本，没有据此声称已测到生产工具延迟。两轮预热、15 次测量、OS 热缓存、新进程，无 AST 常驻缓存；token 用 `o200k_base` 代理。仅 `.ts` 文件，真实源码未人工标注，数量差不能解释成准确率。fixture 仅按调用起始行判分，同一行多节点合并；它不足以证明完整节点级召回。

## 本次 pilot 结果

原始数据：`search-ast-grep-pilot.json`。Windows 11 / Ryzen 7 5800H / 16 逻辑核；rg 15.2.0、ast-grep 0.51.2。仓库快照包含 258 个 `.ts` 文件，共 1,019,483 字节，其中 coding-agent/src 为 26 个文件。6 种查询 × 2 个源码范围 × 3 个引擎配置，加 3 个 fixture 对照，共 39 个 case，各测 15 次。

全仓 `.ts` 范围的耗时如下。范围表示六种查询各自 p50 的最小值至最大值；平均值为这六个 p50 的算术平均，不是混合任务流的 p50。

| 配置 | 查询 p50 范围 | 六个查询 p50 平均值 |
| --- | ---: | ---: |
| 当前 rg 命令形态 | 89.1–94.5 ms | 92.0 ms |
| rg 去掉内部排序，适配层统一排序 | 53.6–58.8 ms | 56.0 ms |
| ast-grep 简单调用 pattern | 87.2–98.1 ms | 94.0 ms |

在这个范围内，rg 排序策略对照的平均值约低 39%。这不是生产工具提速承诺：小目录中同一变更没有改善，且 pilot 不含真实路径检查、glob 前移等完整封装。这里也没有看到 ast-grep 的稳定速度优势。

全仓返回内容的 token 代理值：

| 查询 | rg 行片段 | AST 完整命中节点 | rg 仅路径/行 | AST 仅路径/行 |
| --- | ---: | ---: | ---: | ---: |
| createTool | 1675 | 2230 | 755 | 181 |
| JSON.parse | 2507 | 1824 | 1167 | 1143 |
| runProcess | 175 | 136 | 76 | 46 |
| resolvePath | 938 | 483 | 346 | 223 |

这些行都未触及返回条数上限。两种引擎的返回集合、片段含义不同；真实仓库还未标注正确答案，因此该表只能比较输出大小，不能据此声明相同质量下的节省。`failure` 查询存在截断，原始数据保留了该信息，不把它混入这里的直观比较。

`createTool` 的 AST 完整节点 token 比 rg 高约 33%；仅定位比 rg 仅定位低约 76%，但后者也未包含补读成本与模式漏搜修正成本。输出设计与召回率必须同时评估。

独立 fixture 中，目标是调用起始行 4、5、9、13（直接、非可选的 createTool 调用，包含泛型和嵌套）：

- rg 字面查询：召回 100%，精确率 40%，混入导入、注释、字符串、成员调用和相似名字。
- `createTool($$$ARGS)`：精确率 100%，召回 75%，漏掉第 9 行 `createTool<Context>({})`。
- 另行验证 `createTool<$$$T>($$$ARGS)` 可命中第 9 行；与前一次结果合并后此 fixture 的召回可达 100%。这是一次额外查询，未混入上面的原始性能数据，也不能据此推断所有泛型形式均已覆盖。

这直接验证了方案中的两个风险：返回少未必因为更精准，也可能因为漏搜；AST 需要正确的模板与修正/合并策略。正式 Agent 评估必须把额外查询算入，不能仅用第一条 pattern 的小结果宣传 token 节省。

本次结论：优先比较“优化 rg”与“优化 rg + AST”；暂不替换生产 search。尚未验证完整 Agent 的总 token、任务成功率或端到端延迟。
